# 배송·주문 환불 통합 수동 테스트 유스케이스

## 목적

한 번의 테스트 세션에서 다음 흐름을 모두 확인한다.

```text
결제완료 주문 → 부분 환불 → 잔여 전액 환불 → 배송 상태 전이 → 구매확정
                                  ↘ 결제·배송·PG 예외 처리
```

자동 환불은 `결제완료 + 배송전/배송준비 + 카드 결제키`인 주문만 대상으로 한다.
배송중·배송완료 주문은 상품 회수 후 별도 환불 절차가 원칙이므로, 배송과 자동 환불을 같은 주문에서
순서대로 성공시키면 안 된다. 따라서 아래 유스케이스는 한 번의 실행 큐에서 역할이 다른 주문을 연속으로
사용한다.

## 테스트 실행 단위

| 주문 | 용도 | 필수 초기 상태 |
|---|---|---|
| `REF-A` | 부분 환불과 잔여 전액 환불 정상 흐름 | 카드, `결제완료`, `주문접수`, `배송전`, `paymentKey` 있음 |
| `SHIP-B` | 업체별 배송, 배송완료, 구매확정, 배송 후 환불 차단 | 카드, `결제완료`, `주문접수`, `배송전` |
| `EXC-C` | 미결제·무통장·취소·PG 예외용 복제 주문 | 예외별로 상태를 준비한 별도 주문 |

### 권장 테스트 데이터

`REF-A`는 상품이 2종 이상이고 수량이 남아 있어야 한다.

| 항목 | 예시 |
|---|---:|
| 상품 P1 | 10,000원 × 2 |
| 상품 P2 | 5,000원 × 1 |
| 배송비 | 3,000원 |
| 상품 합계 | 25,000원 |
| 결제 총액 | 28,000원 |

실행 전에 주문번호, 결제키 존재 여부, 상품별 처리 전 재고, 배송비를 기록한다. 금액과 재고는 예시가
아니라 실제 테스트 주문의 값을 기준으로 판정한다.

## 원큐 실행 절차

### 0. 사전 확인

- 관리자 계정으로 `/admin` 로그인
- 고객 계정으로 `/mypage` 로그인할 브라우저 탭 준비
- 카드 결제 환불이 가능한 PG 샌드박스 또는 테스트 결제키 준비
- 관리자 주문 목록에서 `REF-A`, `SHIP-B`, `EXC-C`를 미리 식별
- 각 주문의 현재 상태가 준비값과 일치하는지 확인
- `REF-A`의 상품별 재고를 기록

판정 기준: 테스트 시작 전에 확인한 주문 상태와 재고가 기록되어 있고, 테스트 주문이 실제 운영 주문이
아니어야 한다.

### 1. `REF-A` 부분 환불

1. 관리자에서 `REF-A` 주문 상세를 연다.
2. **상품별 환불 처리**에서 P1의 환불 수량을 `1`로 입력한다.
3. 배송비 포함 체크박스가 비활성화되어 있는지 확인한다. 잔여 상품 전체가 아니므로 배송비를 포함할 수
   없어야 한다.
4. 환불 예정 금액이 `P1 단가 × 1`인지 확인한다.
5. **선택 상품 환불 → 환불 실행**을 누른다.
6. 환불 이력에서 상태가 `완료`인지 확인한다.

기대 결과:

- 환불 금액은 화면에서 임의로 입력한 값이 아니라 주문 당시 단가로 계산된다.
- `REF-A` 결제 상태는 여전히 `결제완료`다.
- P1 재고는 시작값보다 1 증가한다.
- P1 잔여 환불 수량은 1, P2 잔여 환불 수량은 1이다.
- 환불 이력에 성공 건이 1건만 생성된다.

### 2. `REF-A` 잔여 상품과 배송비 전액 환불

1. P1 잔여 수량 `1`, P2 수량 `1`을 입력한다.
2. 배송비 포함 체크박스를 선택한다.
3. 환불 예정 금액이 `P1 잔여 금액 + P2 금액 + 배송비`인지 확인한다.
4. 확인 모달의 상품별 수량과 배송비가 동일한지 확인하고 **환불 실행**을 누른다.
5. 주문 상세를 새로고침한다.

예시 데이터 기준 기대 금액은 `10,000 + 5,000 + 3,000 = 18,000원`이며, 실제 판정은 주문에 저장된
단가와 배송비로 한다.

기대 결과:

- 두 번째 환불 이력도 `완료`다.
- `REF-A` 결제 상태가 `환불완료`로 종결된다.
- 배송비는 두 번째 환불에서 한 번만 포함된다.
- P1 재고는 시작값보다 2, P2 재고는 시작값보다 1 증가한다.
- 새로고침 후 환불할 잔여 수량이 없고, 추가 환불을 실행할 수 없다.
- 성공 환불 총액이 상품 합계와 배송비를 합한 결제 총액과 일치한다.

### 3. `SHIP-B` 업체별 배송 흐름

`SHIP-B`에 여러 업체 상품이 있다면 업체별 배송 카드 각각을 확인한다. 레거시 단일배송 주문이면
**상태 변경 및 관리** 패널을 사용한다.

1. 각 배송 묶음에 유효한 택배사와 운송장 번호를 입력하고 배송 상태를 `배송준비`로 저장한다.
2. 주문 전체 배송 상태가 `배송준비`로 보이는지 확인한다.
3. 첫 번째 배송 묶음을 `배송중`으로 저장한다.
4. 주문 전체 배송 상태가 `배송중`으로 파생되는지, 발송 시각이 기록되는지 확인한다.
5. 첫 번째 묶음만 `배송완료`로 바꾸고, 다른 묶음이 남아 있을 때 주문 전체가 아직 `배송중`인지 확인한다.
6. 모든 묶음을 `배송완료`로 저장한다.
7. 주문 전체가 `배송완료`가 되고 배송완료 시각이 기록되는지 확인한다.
8. 고객 탭의 마이페이지에서 상품별 배송조회와 배송 타임라인을 확인한다.
9. 고객이 배송완료 주문에서 **구매확정**을 실행한다.
10. 관리자에서 해당 배송 카드가 `구매확정`으로 바뀌고, 관리자 입력이 잠기는지 확인한다.
11. 이미 구매확정된 배송에 고객이 다시 구매확정을 눌러도 중복 변경이나 오류 상태가 생기지 않는지 확인한다.

기대 결과:

- 배송 상태는 `배송전 → 배송준비 → 배송중 → 배송완료 → 구매확정` 순서로 관찰된다.
- 일부 업체만 배송중이면 주문 전체를 배송완료로 잘못 표시하지 않는다.
- 관리자가 배송 카드에서 `구매확정`을 직접 선택할 수 없다.
- 구매확정 후 운송장·배송상태를 수정할 수 없다.
- 배송완료 또는 구매확정 이후 자동 환불 UI가 활성화되지 않는다.

### 4. `SHIP-B` 배송 후 환불 차단

1. `SHIP-B` 주문 상세의 **상품별 환불 처리**를 확인한다.
2. 배송이 `배송중` 또는 `배송완료`인 시점에 환불 입력과 실행 버튼이 차단되는지 확인한다.
3. 테스트 환경에서 API 응답까지 확인할 수 있으면 환불 요청이 `refund-after-shipment-not-supported`로
   거절되는지 확인한다.

기대 화면 문구:

> 배송이 시작된 주문은 상품 회수 확인 후 별도 환불 절차로 처리해야 합니다.

### 5. `EXC-C` 예외 분기

아래 주문은 `REF-A`나 `SHIP-B`를 되돌려 재사용하지 말고, 별도 복제 주문으로 실행한다.

| 번호 | 준비 상태 또는 조작 | 기대 결과 | 데이터 불변 조건 |
|---|---|---|---|
| E1 | `결제대기` 또는 `입금대기` 주문에서 환불 패널 확인 | 환불 실행 불가, 현재 결제 상태 안내 | 환불 이력·재고·결제 상태 불변 |
| E2 | 무통장 주문처럼 `paymentKey`가 없는 `결제완료` 주문 확인 | 자동 환불 불가 안내. 수동으로 `환불완료`를 기록하지 않음 | 환불 이력·재고 불변 |
| E3 | `orderStatus=취소완료` 주문에 환불 요청 | 환불 요청 거절 | 추가 환불 원장 없음 |
| E4 | 이미 환불한 상품 수량을 다시 선택 | UI 잔여 수량이 0으로 잠기거나 요청 거절 | 재고 이중 복원 없음 |
| E5 | 일부 상품만 선택한 뒤 배송비 포함 시도 | 배송비 체크박스 비활성화 또는 요청 거절 | 배송비 중복 환불 없음 |
| E6 | 환불 수량을 주문 잔여 수량보다 크게 입력하거나 다른 상품 ID로 요청 | 요청 거절 | 주문 상태·재고·환불 이력 불변 |
| E7 | 환불 확인 모달에서 취소 또는 `Esc` | 모달만 닫히고 환불 요청이 발생하지 않음 | 환불 이력·PG 호출 없음 |
| E8 | 환불 실행 버튼을 빠르게 연속 클릭 | 한 건만 처리 | 환불 원장 1건, 재고 1회 복원 |
| E9 | PG가 4xx로 환불 거절하도록 샌드박스 설정 | 이력 `실패`, “결제사가 환불 요청을 거절했습니다” 안내 | 주문은 `결제완료`, 재고 불변 |
| E10 | PG 응답을 타임아웃·네트워크 오류로 끊음 | 이력 `확인 필요`, 같은 요청을 무작정 반복하지 않도록 안내 | PG 잔액과 원장을 먼저 대조 |
| E11 | PG 환불은 성공했지만 원장 확정 단계가 실패하도록 설정 | `확인 필요`, “결제사 환불은 진행됐지만 주문 원장 반영이 지연” 안내 | PG 상태 확인 전 재시도 금지 |
| E12 | 배송완료 전 구매확정 또는 미결제 주문에서 구매확정 시도 | 구매확정 거절 | 배송 상태와 확정 시각 불변 |
| E13 | 구매확정된 배송 카드의 운송장·상태 수정 시도 | 수정 거절 또는 저장 불가 | 구매확정과 확정 시각 불변 |

PG 거절·타임아웃·원장 확정 실패는 일반적인 정상 샌드박스 결제만으로는 재현되지 않을 수 있다.
테스트 환경에 PG fault injection, 네트워크 차단, 또는 테스트용 결제 어댑터가 없으면 해당 항목은
`재현 불가`로 기록하고 통과로 처리하지 않는다.

## 환불 예외 시 확인 순서

`실패` 또는 `확인 필요`가 발생하면 다음 순서로 확인한다.

1. 관리자 주문의 환불 이력 상태와 오류 메시지를 캡처한다.
2. PG 결제 잔액과 새 취소 거래가 실제로 생성됐는지 확인한다.
3. 주문의 `paymentStatus`와 상품 재고를 확인한다.
4. `확인 필요`인데 PG 환불이 이미 완료된 경우, 원장 중복 생성 없이 재조정 절차를 사용한다.
5. PG 상태를 확인하지 않은 채 새 결제키나 새 idempotency key로 재시도하지 않는다.

## 최종 합격 기준

- [ ] `REF-A` 부분 환불이 성공하고 결제 상태가 `결제완료`로 유지된다.
- [ ] `REF-A` 잔여 전액 환불 후 결제 상태가 `환불완료`가 된다.
- [ ] 환불 금액이 주문 단가·수량·배송비와 일치한다.
- [ ] 성공 환불 수량만큼만 재고가 복원되고, 재시도해도 이중 복원되지 않는다.
- [ ] 배송 상태가 단계별로 저장되고, 다중 배송 묶음의 주문 상태 파생이 정확하다.
- [ ] 배송완료 후 구매확정이 가능하고, 구매확정 후 배송 정보가 잠긴다.
- [ ] 배송중·배송완료·구매확정 주문의 자동 환불이 차단된다.
- [ ] 미결제·무통장·취소·중복·수량초과·배송비 조건 예외가 모두 차단된다.
- [ ] PG 거절은 `실패`, 결과 불명은 `확인 필요`로 구분된다.
- [ ] 어떤 예외에서도 주문 상태, 환불 원장, 재고가 부분적으로만 바뀌지 않는다.
